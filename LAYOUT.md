# Layout

What goes where, by what a file is for. `pkgs/` holds only packages: a
file that packages of different families share goes in a top-level folder
named after what it holds, and a new kind gets a folder of its own (or a
better name for the old one).

- `pkgs/<name>/` holds everything of one package; the files a family of
  packages shares sit in one of them (`pkgs/microsoft-office` for the
  Office apps).
- `verify/` holds the checks packages of different families share: that a
  download is upstream's (Apple code and installer signatures, against the
  pinned Apple root CA) and that an installed app is the pinned one.
- `lib/` holds Nix functions and values the packages and modules share.
- `modules/` holds the modules that belong to no one package.
- `scripts/` holds the tools the packages' `update.sh` scripts use.
- `firewall/` holds firewall rules for the users of the packages: a Little
  Snitch rule group that cuts app updaters off the network.
- `ci/` holds the CI and update machinery the workflows run, which no
  package reads.

Nix rebuilds a derivation when a file it references changes, wherever the
file lives, so a change in `verify/`, `lib/` or `scripts/` rebuilds only the
packages that read that file. A change in `ci/` or `check.yml` makes CI
build every check on every system (`ci/check-plan.sh`).

| Path | Role |
|---|---|
| `AGENTS.md`, `CLAUDE.md` | Guidance for coding agents. `CLAUDE.md` only imports `AGENTS.md` for Claude Code, so the guidance stays in one file. |
| `SECURITY.md` | How to report a vulnerability, and the trust model: what pins, checks and sandboxes do and don't cover. Keep it in sync with the workflows, `ci/`, `verify/`, `lib/`, `scripts/` and the modules. |
| `flake.nix` | Discovers `pkgs/*/package.nix` and the module files; builds all packages in one `makeScope` so they can depend on each other by argument name; filters `packages.<system>` with `lib.meta.availableOn`, except for the packages in `fixedPlatforms` (they fetch Hermes' flake when evaluated). `checks` builds every package but the `rolling` ones (`ghostty-tip`, whose pin expires with each upstream build) and the `heavy` ones (the Office apps, a ~1.4 GB download and ~3 GB built each, which `microsoft-office.yml` builds instead, and `microsoft-office`, which joins them) and adds `warp-exclusions` (mock-CLI split-tunnel reconciliation tests), `warp-launchd-syntax` (generated launchd shell scripts with exclusions disabled, enabled individually, and combined), `formatting` (`nixfmt --check`) and, on Linux, `lint` (shellcheck over the shell scripts, actionlint over the workflows), `pkg-signature-sync` (the two installer signature checks' shared verification identical) and the module checks, each a configuration with every module of its kind imported and enabled, evaluated: `nixos-modules` (NixOS), `darwin-modules` (nix-darwin, Apple Silicon), `home-modules` (standalone Home Manager on that Linux system, as on Ubuntu) and `darwin-home-modules` (Home Manager on macOS). The `nix-darwin` and `home-manager` inputs exist only for these checks and follow `nixpkgs`. `devShells.<system>.default` holds the tools those checks run, from the same nixpkgs; keep its list in sync when a check starts using another tool. |
| `overlays/default.nix` | `pkgs.xr3t.<name>`, built against the consumer's nixpkgs. |
| `pkgs/<name>/package.nix` | The derivation. Read `version`/hashes from `hashes.json` for prebuilt binaries. |
| `pkgs/<name>/hashes.json` | `{ "version": ..., "hashes": { "<key>": "sha256-..." } }`, written by `update.sh`. Keys are whatever the package looks up (usually the system). Exception: `hermes-agent` pins an upstream flake as `{ version, rev, narHash }`. |
| `pkgs/<name>/update.sh` | Optional. Bumps `hashes.json` to the latest upstream; no-op when current. Run by `.github/workflows/update.yml`. Sources `scripts/update-lib.sh`. |
| `pkgs/<name>/module.nix` | Optional. `self: { config, ... }: { ... }`; exported as both `darwinModules.<name>` and `nixosModules.<name>`. Default package is `self.packages.${system}.<name>`. |
| `pkgs/<name>/nixos-module.nix`, `darwin-module.nix` | Same shape as `module.nix`, exported only to `nixosModules` or `darwinModules`. |
| `pkgs/<name>/home-module.nix` | Same shape, exported as `homeManagerModules.<name>`. |
| `pkgs/<name>/*.asc` | Optional. An upstream release signing key that `update.sh` checks signatures against (`claude-code`), pinned by fingerprint in the script. |
| `pkgs/<name>/*.mobileconfig` | Optional. A macOS configuration profile the package ships for the user to approve, for a setting the app reads only from managed preferences (`claude-desktop`). |
| `pkgs/<name>/README.md` | Optional. The package's usage, options and maintenance notes. |
| `pkgs/README.md` | The package table: each package, what it brings and the systems it runs on, in alphabetical order. The top-level README links to it. |
| `pkgs/microsoft-office/builder.nix` | The builder the Office app packages (`microsoft-excel`, `microsoft-powerpoint`, `microsoft-word`) share: checks the installer with `verify/office-pkg-signature-check.py`, extracts the app component into `out` and the licensing helper into `licensing`. In the `microsoft-office` package directory, not `ci/`: only the Office apps use it. |
| `pkgs/microsoft-office/update-lib.sh` | Sourced by those packages' `update.sh`: follows Microsoft's download link, waits for MAU's manifest to offer the same build, checks the installer's signature and takes its version from the signed `Distribution`. |
| `pkgs/google-drive/apfs-cat.py` | Copies a file out of an APFS volume image with `dissect.apfs`: Google Drive's dmg is APFS, which `undmg` and 7-Zip can't read. |
| `pkgs/cloudflare-warp/apply-exclusions.sh` | Consumer WARP exclusion reconciliation used by the service module and `warp-apply-exclusions`. |
| `pkgs/cloudflare-warp/tests.py` | Offline mock-CLI tests run by `checks.<system>.warp-exclusions`. |
| `verify/check-app.py` | Install check for a macOS app bundle: its executable exists, and its version is the pinned one; optional build-number and native Mach-O architecture checks. |
| `verify/codesign-check.py`, `verify/apple-root-ca.pem` | Checks Apple code signatures without macOS (`rcodesign`, `openssl`): a Mach-O file's every slice intact (one SHA-256 code directory, each code page against its signed hash; `rcodesign verify` too, but for its complaint about Go binaries' `__LINKEDIT` placement) and signed by a Developer ID Application certificate of the given team chaining to Apple's root CA (pinned by fingerprint in the PEM): Apple's Developer ID Application extension, and the team as the subject's only OU and in its only CN, each field compared whole; for an `.app` or `.framework`, also its whole seal (`Info.plist`, `CodeResources`, every listed file, nested code by cdhash, nothing unsealed). A package that exposes it as `passthru.codesign` on its Linux package too gets `checks.<linux>.<name>-codesign`, macOS-only packages included (`anoa`, `claude-code`, `claude-desktop`, `firefox`, `google-drive`, `kiri`, `santa`). |
| `verify/pkg-signature-check.py` | Checks a macOS installer package (`.pkg`, xar) without macOS (`openssl`): its table of contents signed (RSA and CMS) by a Developer ID Installer certificate of the given team chaining to Apple's root CA (`verify/apple-root-ca.pem`), matched by field as `verify/codesign-check.py` does (Apple's Developer ID Installer extension, the team as the only OU and in the only CN), and every file matching the checksum recorded there; then prints a bundle's version from the `Distribution` or writes one file (a component's `Payload`) to stdout. Used by `google-drive` and other packages that check a `.pkg`. |
| `verify/office-pkg-signature-check.py` | The same check, the Office apps' own: a change to `pkg-signature-check.py` for another package doesn't rebuild them (a ~1.4 GB download each). What decides whether a package is trusted sits between `BEGIN`/`END shared verification` markers in both files, and `checks.<linux>.pkg-signature-sync` fails when the two differ there. |
| `lib/read-only-app-copies.nix` | The activation entries that keep apps in Home Manager's copy folder (`targets.darwin.copyApps`) read-only between activations, unlocked before Home Manager's App Management check and copy; `modules/read-only-apps.nix` uses them for the whole folder, the `whatsapp` module for its own bundle. |
| `lib/app-copy-launcher.nix`, `lib/app-copy-launcher.sh` | The command a macOS app package installs for an executable inside its bundle (`anoa`, `zed`): runs it from Home Manager's or nix-darwin's copy of the bundle when the copy is this build (executable, `Info.plist` and `CodeResources` identical), else from the store, so LaunchServices never registers the store bundle. |
| `modules/read-only-apps.nix` | `homeManagerModules.read-only-apps`: the `targets.darwin.copyApps.readOnly` option, which keeps every app Home Manager copies, and their folder, read-only. Exported by `flake.nix` beside the packages' `home-module.nix` files. |
| `lib/hardening.nix` | The systemd sandboxing the opt-in `hardening.enable` options share (`serviceConfig`); each module adds what its service can live without. Modules otherwise run services as upstream's installer does. |
| `scripts/macos-app-release.py` | Selects the newest stable WhatsApp or native Telegram version/build from the official Sparkle feed; validates the download URL against each vendor's release endpoint. |
| `scripts/update-lib.sh` | Helpers for `update.sh`: `check_version` (rejects unexpected upstream versions), `gh_latest`, `skip_if_current`, `prefetch` (checks a download against upstream's sha256 when given one, and a GitHub release asset against GitHub's digest), `write_hashes` (with `sums` set, against upstream's checksum list or per-file `.sha256`). |
| `firewall/updaters.lsrules`, `firewall/README.md` | A Little Snitch rule group (macOS) denying the network to app updaters, matched by code signature: the updaters that run as processes of their own (Google's GoogleUpdater and Keystone, Microsoft AutoUpdate) everywhere, and apps that update from inside their own process (Telegram, Ghostty) towards their update hosts only; users subscribe to it by its raw URL. `checks.<linux>.firewall-rules` checks its JSON, that every rule denies a code ID, and that it names its remote. |
| `ci/update-all.sh` | What `update.yml` runs, once per `UPDATE_SYSTEM` (without `PACKAGES`, all but `ON_REQUEST`'s): every `update.sh` of that system's packages (`x86_64-linux`: all that build there; `aarch64-darwin`: those that build only on macOS), each update built (`nix flake check --keep-going`) before it lands, and on Linux the weekly bump of `nixpkgs` with `nix-darwin` and `home-manager`. A package that `checks` leave out (rolling, heavy) is deleted from the store again once built, so the macOS job's store cache doesn't keep it. Git pushes and fetches go through `gh`'s credential helper with `GH_TOKEN`, as `update.yml`'s checkouts keep no token. An `update/<name>` branch that `main` has moved past is proposed again on top of `main`. After proposing an update it runs `ci/drop-approval-runs.sh`. |
| `ci/drop-approval-runs.sh` | Deletes the `pull_request` runs that GitHub holds for approval on a pull request `GITHUB_TOKEN` opened or pushed to (they would fail once the dispatched `check.yml` merges it), waiting up to a minute for them to appear. Run by `ci/update-all.sh` and `ci/merge-update.sh`. |
| `ci/merge-update.sh` | Run by `check.yml`'s `merge` job once every system passed on an `update/<name>` branch: when the tested head contains `main`, deletes that commit's `pull_request` runs still waiting for approval, merges the pull request, deletes the branch and starts `cache.yml` on `main`; when `main` has moved past it, rebases the branch onto `main`, pushes it and starts `check.yml` there again. |
| `ci/changed-checks.sh` | Prints the checks of a system whose derivation differs from those at a git revision (all of them without one); `check.yml` builds only those. Evaluation only, so it runs on Linux for every system. |
| `ci/check-plan.sh` | Run by `check.yml`'s `plan` job, on Linux. For each system, selects the checks that differ from the newest successful ancestor Check run of this repository (a pull request's, a dispatch's, or an earlier push to `main`'s), and outputs one matrix entry per system that has any; falls back to all checks without a baseline or when check machinery changes (`check.yml` or `ci/`). Also evaluates every package of every system and builds `formatting`. |
| `ci/cached-packages.sh` | The packages CI pushes to ret.cachix.org, those that compile for minutes (`hermes-agent`, x86_64 only, and `llama`), filtered to a system; read by `cache.yml` and `update.yml`. |
| `ci/cache-plan.sh` | Run by `cache.yml`'s `plan` job: per Linux system, the cached packages whose output ret.cachix.org doesn't hold yet. |
| `ci/macos-cache-key.sh` | Hashes macOS package derivations (including rolling packages) for the store cache `update.yml`'s macOS job keeps between runs; Linux-only changes do not replace it. |
| `.github/workflows/check.yml` | On pull requests (checked out at their head, not GitHub's merge commit) and on Run workflow; `main` gets no run of its own. A `plan` job on Linux evaluates every system's checks and packages, builds `formatting`, and lists per system the checks that differ from a successful ancestor run (`ci/check-plan.sh`); one runner starts per system with any (Linux x86_64, Linux aarch64, macOS), to build just those, with no store kept between runs, so a change to macOS packages alone starts only the macOS runner, and the Linux runners only for the packages with a `-codesign` check. `Validate all systems` passes once all of them did; the tested head is the tree that lands while it contains `main` (the `merge` job ensures that for update branches; other pull requests are brought up to date before merging). No branch rule requires it: one would also reject `update.yml`'s direct pushes to `main`. Cancels older Check runs for the same branch, with PR events separate so they cannot cancel update merges; read-only token, not kept in the checkout; pushes nothing to Cachix. When `update.yml` starts it on `update/<name>` and all systems pass, its `merge` job runs `ci/merge-update.sh`. |
| `.github/workflows/cache.yml` | On a push to `main`, or when `update.yml` or `check.yml`'s `merge` job starts it after landing an update (their token's merges and pushes start no workflow): builds the packages of `ci/cached-packages.sh` that ret.cachix.org doesn't hold yet at `main`'s version (`ci/cache-plan.sh`), on the Linux runner of their system, and pushes their runtime closures; nothing when the cache holds them all, or without a Cachix token. Only from `main`; the token reaches only the push step. |
| `.github/workflows/update.yml` | Three times a day (05:17, 13:17, 21:17 UTC), one run at a time: runs `ci/update-all.sh` on Linux, then on macOS for the macOS-only packages, so each update is built on a system it runs on; skips the packages in `ON_REQUEST` (the Office apps) unless its `packages` input names them; checks the flake, commits `Update <name> to vX.Y.Z` to `main`, or for the packages in `REVIEW` opens a pull request from `update/<name>` and starts `check.yml` on it, which merges it once green; the macOS job keeps its Nix store between runs with cache-nix-action (it builds every macOS check for each update; heavy packages are deleted before the store is saved); on Monday's first run (or when asked for) updates the `nixpkgs` input the same way, always as a pull request (`update/nixpkgs`); then pushes the x86_64 closures of `ci/cached-packages.sh` to ret.cachix.org and starts `cache.yml` on `main` for the aarch64 ones. |
| `.github/workflows/microsoft-office.yml` | Only on request: a pull request to `main` that touches the Office apps or their builder and carries the `build-office` label, or Run workflow on a branch (compared with `main`): a `plan` job on Linux compares their `aarch64-darwin` derivations (their only system) with the base branch, and a macOS (Apple Silicon) runner builds only the apps that differ, one at a time, each deleted from the store before the next. Read-only token, not kept in the checkout, no secrets; not a required check (its `paths` filter would leave other pull requests waiting). Pull requests `update.yml` opens don't run it: `update.yml` builds those bumps itself. |
| `.github/dependabot.yml` | Weekly bumps of the actions, which workflows pin by commit SHA. |
